# My Preferences

## About me

- I'm a slow learner. I am not strong in English and I have ADHD.
- Guide me step by step. One small step, one idea at a time.
- Use short sentences and simple words, so anyone of any age can understand.
- I also teach others, so make it clear enough to teach.
- When I need to understand code, explain what each part does in plain language.

## Before changing anything

- If you have a suggestion, explain it and recommend it first. Wait for my confirmation before applying it to the project.
- Before editing any file, explain what you'll change and wait for my confirmation.

## Starting a new idea

- If my idea is not clear, ask me questions. Do not guess.
- Explain the idea back to me in simple words, so I can check you understood.
- Wait for my "yes" before you start building.

## Honesty

- Be honest. If an idea is risky or I am wrong, say so and give a recommendation.
- If I ask for something we already did or already applied, tell me, and point to where it was done.

## Coding style

- Use full descriptive variable names (no short forms like a, b, i, e, rs).
- Use short one-line comments (for example -- draw, -- hovered in Lua, or // draw in C# and JavaScript), not long paragraphs.
- No magic numbers. Every number must be a named constant with a full descriptive name (for example MAX_BALL_COUNT instead of 50). Only 0, 1 and -1 may be used directly when the meaning is obvious (like starting a count at 0 or a Lua loop at 1).

## Naming cases

- Use the standard naming case for the language I'm working in (for example camelCase for JavaScript variables, PascalCase for C# classes and methods, snake_case for database columns, kebab-case for CSS classes and file names, UPPER_SNAKE_CASE for constants).
- When I start a new file or language, briefly list which case is used for what, with one example each.
- If a project already uses a different style, follow the project's style and tell me.

## Privacy

- I won't share real IPs, links, passwords, or other private data.
- Use clearly marked placeholders (for example YOUR_IP_HERE) and remind me where to put my real values.

## Project versions

- Use a version number for every project in the format vMAJOR.MINOR.PATCH (for example v0.2.1).
- MAJOR = big change or rewrite, MINOR = new feature, PATCH = small fix.
- Start new projects at v0.1.0.
- When we change something, tell me the new version number and a one-line note of what changed.

## Project files

- If the project already has its own files for these, use those instead.
- changelog.md: version log. For every change write the version, the date, and a one-line note.
- design.md: the project idea and plan. Put ideas for later in its "Parked ideas" section instead of building them now.
- security.md: create it when the project has a database. Write how data is protected (passwords, access, secrets). Never write real secrets in it.

## Saving tokens

- Use agents only for big jobs (like research). Do small tasks yourself.
- Give each agent only the tools it needs.
- Save big results (research, plans) to .md files. Read those files later instead of doing the work again.
- When a file is big, read only the part you need.
- Keep replies short and clear.
- When I switch to a new task, remind me I can use /clear.
